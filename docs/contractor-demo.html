Contractor Demo

The hello-world contractor demo shows the intended operating model: Codex acts as architect and project manager, Beads records the work graph, Antigravity through agy and Claude Code receive bounded contracts, and contractor output is reviewed before it becomes project direction.

Project

The demo repository is a small static site, intentionally simple enough that the contractor workflow is the subject. Codex created the baseline project, posted Beads-backed assignments, dispatched two outside tools through manual prompts, reviewed both returns, repaired public-doc issues, integrated accepted work, and published GitHub Pages.

In-Codex Invocation

Start with one compact prompt coach request. The coach should size the graph before packet creation and still ask the collaboration, parallelism, validation, and publish questions. 

/plan Use $complex-work-orchestration prompt coach for a hello-world contractor demo:
Beads graph, Codex PM + review, agy -p docs branch, claude -p Pages branch.
Ask before external sharing; choose subagent parallelism; set validation + publish gates.

After reviewing the plan, the operator can approve execution in the same Codex conversation. Codex should create the Beads graph first, keep one contractor Bead and one patch branch or worktree per outside tool, render packet-backed manual prompts, and treat returned contractor work as evidence until architect review accepts it.

Executor Access

The Codex runtime account must be able to invoke the approved contractor CLIs, such as agy -p and claude -p, or it must have operator-approved privilege escalation to an operating-system account that can run those commands. That escalation is prearranged environment setup; Codex should not discover, mint, or own credential escalation while launching the contract. Without that access, Codex can still prepare a packet and rendered prompt, but the actual dispatch becomes a separate operator action.

Access boundary: Privilege escalation is environment setup, not contractor authority. A contractor packet does not grant shell access, credentials, repository ownership, or permission to bypass the approved share boundary. External CLIs receive only the rendered prompt and sanctioned packet artifacts, not Beads authority, repo policy control, or merge permission.

Keep this prerequisite generic in public docs. State that the runtime account needs direct CLI access or approved escalation, but do not publish local usernames, private home paths, sudoers rules, hostnames, or account-specific command transcripts.

Dispatch Lessons

Packet generation is not dispatch. The PM first creates a contractor Bead, builds a policy-checked packet, then renders a manual prompt. The operator executes the prompt with the approved external CLI and captures the return artifact for review. 

python3 scripts/build_contractor_packet.py \
  --bead "$BEAD_ID" \
  --executor claude_code_manual \
  --share-boundary patch-branch \
  --allow-disclosure-escalation \
  --external-ok \
  --format json \
  --output contractor-packet.json

python3 scripts/dispatch_work.py \
  --packet contractor-packet.json \
  --mode manual \
  > contractor-dispatch-prompt.md

Use an isolated worktree or patch branch per contractor. When a contractor tool runs under a different operating-system account, arrange access so repository commands still run as the repo owner and keep that detail out of public documentation. For agy -p, pass the intended working directory when the tool supports it. For claude -p, make the prompt explicit about the branch, allowed paths, and command boundary. Capture tracked workspace state before and after tool-running contractors so unexpected mutation is review evidence. 

python3 scripts/workspace_mutation_guard.py \
  --snapshot \
  --output before.json

agy -p "$(cat contractor-dispatch-prompt.md)" \
  > contractor-return.md

python3 scripts/workspace_mutation_guard.py \
  --compare before.json \
  --output mutation-report.json
Ignored artifacts: Packet JSON, rendered prompts, and contractor returns are useful evidence, but they should normally stay out of the public commit unless intentionally sanitized and published.

Return Review

Contractor output is evidence, not authority. Normalize and evaluate returns before using the work. Parser or heuristic failures should trigger architect review; they are not automatic proof that the patch is bad, and they are not permission to skip review. 

python3 scripts/normalize_contractor_return.py \
  --bead "$BEAD_ID" \
  --dispatch-id "$DISPATCH_ID" \
  --packet-sha256 "$PACKET_SHA256" \
  --file contractor-return.md \
  --workspace-mutation-report mutation-report.json \
  --output contractor-return-bundle.json

python3 scripts/evaluate_return.py \
  --bead "$BEAD_ID" \
  --file contractor-return.md \
  --workspace-mutation-report mutation-report.json

The demo exposed two practical quality gates. Return headings should use the canonical labels expected by the evaluator, and unexpected tracked-file mutation should block direct use until architect review. Public docs also need a human editor pass for incorrect attribution, absolute paths, file:// links, fabricated validation claims, and unclear ownership.

Validation

The final acceptance gate combines repository validation, public docs checks, publish sanitization, GitHub Actions status, Pages deployment, live HTTP verification, and closed Beads evidence.

  1. Run local validators before merging contractor branches.
  2. Scan tracked files for private paths, local URLs, tokens, and private key markers.
  3. Record accepted and rejected contractor findings in Beads.
  4. Close the publish task only after CI, Pages deployment, and live content checks pass.
  5. If Beads has no Dolt remote, say the work graph is local-only.
Operator takeaway: Outside tools can produce useful patches, but the durable work story, acceptance decision, and public release remain Codex PM and architect responsibilities. Use the external contracting guide for the exact packet, label, and return-review controls.
