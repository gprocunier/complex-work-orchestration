Install the Skill

A Codex skill is a local instruction pack that Codex can load during a conversation. Install CWO into your Codex skills directory, then invoke it from the Codex prompt.

Clone the repository and run the guided installer. It detects a Codex skills directory from CODEX_SKILLS_DIR, CODEX_HOME, or $HOME/.codex/skills, then prompts before copying files. 

git clone https://github.com/gprocunier/complex-work-orchestration.git
cd complex-work-orchestration
./scripts/install.sh

For unattended installs, pass the destination explicitly: 

./scripts/install.sh --skills-dir /path/to/codex/skills --yes

The installer verifies the copied skill with a source-vs-installed content manifest and writes .cwo-install-manifest.json inside the installed skill. Check an existing install without modifying it: 

python3 scripts/check_installed_skill.py --check

If the checker reports missing or drift, rerun the installer against the same Codex skills directory to reload the skill.

Beads is required for the durable workflow. The skill installer only warns when bd is missing so the documentation can still be installed and read. 

command -v bd
bd version

On Fedora, RHEL, or compatible systems, use your own Beads package source if you have one. Otherwise the installer points at the public greg-at-redhat/beads COPR. Set BEADS_COPR=owner/project before running the installer to show a different COPR hint. 

sudo dnf copr enable greg-at-redhat/beads
sudo dnf install beads

For other platforms, use the upstream Beads project at github.com/steveyegge/beads.

Choose Your Profile

Start by naming where the work will run. CWO is the governance layer; the execution environment is the shell, provider boundary, and model profile that can actually do the work.

Connected Single Operator

Use the in-Codex coach, one local Beads graph, focused tests, and normal validation. This is the fastest first run.

Choose this when you have Codex, repository access, and a normal network connection. Do not choose it for airgapped or shared-operator environments.

Connected With Contractors

Add Claude, Gemini, ChatGPT Pro, or another approved reviewer only after the sharing boundary and packet are explicit.

Choose this when a second opinion is worth the disclosure and review overhead. Do not choose it for private context that cannot leave the machine.

Restricted OpenCode

Render bounded dispatch envelopes for OpenCode or a manual operator shell while keeping Beads, evaluator scoring, and architect adjudication.

Choose this when Codex is not the right execution shell but the workflow can still use local project state. Do not choose it if no approved shell can run the assignment.

Airgapped Or RHOAI

Assume no public frontier calls. Use local Beads plus approved OpenAI-compatible RHOAI/vLLM model profiles or manual operators.

Choose this when public services are unavailable or forbidden. Do not choose it until local model endpoints and operator handoff rules are known.

If you are unsure, use the connected single-operator path first and let the coach recommend whether a broader work graph, model synthesis, local worker, or contractor handoff is justified.

Run the Coach

In Codex, start with the prompt coach when the right amount of orchestration is unclear. Codex can run the local helper, show the recommended level, and ask any interactive questions before execution starts. 

/plan Use $complex-work-orchestration prompt coach:
Clean up installer docs, tests, and handoff notes.

The simple path is five steps: ask for the coach, answer any execution-changing choices, create or update one Beads task, validate the work, and close the task with a recovery-quality closure-memory comment. The simple use case shows that sequence without the full contractor workflow.

Codex may run this helper behind the scenes. Use direct script execution only for automation, CI, troubleshooting, or an operator shell outside Codex.

Operator Reference: Coach Helper 
python3 scripts/coach_prompt.py \
  "Clean up installer docs, tests, and handoff notes."
Default posture: The skill always expects durable Beads tracking. Narrow work can stay in the current thread, but it should still leave one Beads task with evidence and validation notes.

Core Terms

These terms appear in the first run. Learn only these first, then use the workflow and reference pages when you need exact controls.

Codex

The coding-agent shell where you invoke the skill and where the main thread keeps final judgment.

CWO

Complex Work Orchestration: the workflow that sizes, records, reviews, validates, and hands off complex agent work.

Prompt Coach

Sizes a request before execution so Codex uses the right amount of tracking, review, and validation.

Beads

The durable task graph for scope, dependencies, evidence, validation, closure memory, and handoff.

Epic

A parent Bead for a larger goal. Small first runs usually need only one task, not a full epic.

Dolt Remote

An optional sync target for Beads. Without one, the work graph is durable on this machine but not shared elsewhere.

Validation

The checks that prove the work is ready, such as tests, docs validation, install smoke, or Pages deployment.

Closure Memory

The final Beads comment that explains what happened, how it was checked, and what a future agent should know.

Review Worker

A bounded helper that gathers evidence while the main Codex thread keeps final judgment.

Contractor Packet

A policy-checked brief for an outside or local model reviewer, built only after the sharing boundary is approved.

Evidence Lane

A contractor, local worker, or peer review return that must be evaluated before it can affect implementation.

Run Readiness

A pre-handoff gate for broad runs that proves owners, exit conditions, evidence, and validation are in place.

Record Beads

Use Beads as the shared work story. If the repository should own the durable state, initialize it once. If a Dolt remote is configured, pull before handoff work and commit or push after recording evidence. Without a remote, the graph is durable local state on this machine but not shared across machines.

Operator Reference: Beads Checks 
command -v bd
test -d .beads && bd ready --json || true
bd init
bd dolt remote list
bd dolt pull
bd dolt commit
bd dolt push

If Beads is unavailable or cannot be installed, record the same task or graph structure in a temporary Markdown plan file and note that durability is reduced. The full workflow and fallback limits are covered in Workflows.

When the work closes, the useful memory should be in the final comment, not the terse close reason. Capture who was involved, what changed, why it closed, how it was validated, when it closed, where it ran, any residual risk, and follow-up.

Operator Reference: Closure Comment 
bd comment "$BEAD_ID" --body "$(cat <<'EOF'
Closure memory:
- Who: Codex main thread; reviewer lane if applicable.
- What: Changed docs, validation, or handoff artifact.
- Why: Accepted and ready to close.
- How: Validation command, CI run, install smoke, or review evidence.
- Where: Repository, branch, and Beads local-only or Dolt-backed mode.
- Residual risk: None known, or the exact remaining risk.
EOF
)"

Generated Beads populate native fields for skills, acceptance, design, and notes. The description remains the readable assignment body. When creating Beads manually, use real newlines through a heredoc, --body-file, --design-file, or command substitution instead of typing literal \n sequences.

Worker-facing ready work should exclude contractor and local worker guard labels:

Operator Reference: Ready Work Filter 
bd ready \
  --exclude-label contractor-only \
  --exclude-label local-worker-only \
  --exclude-label no-codex-exec \
  --json

Execute Safely

Let the coach decide whether the work stays in the current Codex thread, becomes a lightweight Beads task, or needs a larger work graph. Outside reviewers and local workers are optional paths selected later; they are not the starting point.

  1. Invoke the skill from Codex when sizing is unclear.
  2. Let Codex route non-trivial work against the policy.
  3. Create a Beads task, or an epic when the goal has several dependent parts.
  4. Run validation before accepting findings or publishing.
