Why The Workflow Is Structured This Way

A coding-agent shell can do real project work, not just answer questions. CWO adds the structure that keeps that work recoverable, reviewable, validated, and ready for handoff.

From Chat To Shell

Web-chat AI is strongest when you need an answer, draft, summary, or thought partner. A coding-agent shell is different: it can work inside a repository, edit files, run tests, inspect command output, and verify the result.

That power creates a new problem. The work can outgrow the chat transcript. Decisions need to be recorded, reviews need boundaries, validation needs evidence, and the next agent needs a clean place to resume.

Role Separation

Candidate E is CWO's default instruction profile for the Codex session that owns scope, integration, acceptance, and handoff. That session also resolves design tradeoffs, validation judgment, and release decisions. For larger work, project-management coordination keeps the work graph current and makes sure each lane has a clear assignment and handoff.

Review workers, outside models, and local models are deliberately narrower. They investigate, critique, summarize, or return a bounded patch. Their output is useful because it is focused, but it is not authority. The main thread still decides what to accept.

Why Native Work Is Supervised

Delegation should not transfer decision authority. In the normal connected path, Candidate E can assign a narrow implementation or validation task to one fresh Spark worker. The local supervisor—the trusted controller outside the worker—verifies the model, binds the assignment, watches tools and workspace changes, and enforces time and token limits.

The order matters: persist the supervision state and register the observer before sending work, then observe the task before cleanup. If identity, telemetry, interruption, workspace attribution, or a required receipt is missing, CWO stops rather than treating worker prose as proof. Every delegated native worker is supervised; there is no unsupervised mode or opt-out. The Native Supervision guide separates mandatory supervision from the optional multi-worker concurrency Tech Preview.

Durable Memory

Chat history is not a reliable project database. A spawned agent may start with no transcript, and a long-running session may be compacted into a fuzzy summary. Beads is the durable task graph CWO uses to record task scope, dependencies, evidence, decisions, validation, and handoff notes.

This is why CWO is positioned above model and agent tools rather than as a replacement for them. OpenRouter Fusion can provide multi-model deliberation; LangGraph, AutoGen, and CrewAI can run agent workflows; Claude Code, Gemini CLI, and Codex CLI can work directly on code. CWO records the boundary, provenance, evaluation, and closure rationale around those surfaces.

That is why meaningful closures need a final summary before the task is closed. The close reason stays short; the useful memory lives in the comment: who was involved, what changed, why it closed, how it was validated, when it closed, where it ran, what risk remains, and what should happen next.

Local-only mode: If the repository has no Beads remote, the graph is still useful durable local state. It is not synced to another machine until a remote exists and the operator pushes it.

The Beads Memory deep dive explains how closure comments and context-depth choices help spawned agents and compacted sessions recover the work story.

Evidence Boundaries

Outside and local model workstreams are opt-in. A handoff packet defines what can be shared, which files or snippets are allowed, what question is being asked, and how the return will be judged. A contractor can provide a strong second opinion, but the return is still evidence until it is evaluated and adjudicated.

This matters most when a tool can see more than the packet was supposed to expose. If a redacted review accidentally uses local repository context, that extra evidence should be rejected or quarantined instead of folded into the plan without review.

Publication Quality

Public documentation has a different bar than internal planning. A reader should see prerequisites, the first action to take, the reason behind a workflow, and the reference surface when they need exact commands. They should not have to sort through planning labels, draft notes, repeated lifecycle prose, or private implementation assumptions.

That is the purpose of the final editorial review for public docs and GitHub Pages: check the reader journey, remove repeated or circular wording, keep rationale where it helps, and make sure operator details are presented as reference material.

Failure Modes The Harness Avoids

  1. Starting a large task without a durable work graph.
  2. Letting contractor output become implementation authority.
  3. Sending native work before the supervisor and observer are ready.
  4. Publishing docs that expose internal planning language.
  5. Repeating the same workflow across several pages until they drift.
  6. Claiming validation, sync, or share-boundary behavior that did not happen.
