Policies

The skill is a small control plane over Beads task tracking: policy chooses routes, schemas define exchanged artifacts, experts calibrate review lenses, and scripts enforce gates.

Policies are JSON-compatible YAML files used by helper scripts. They describe route classes, executors, providers, experts, sharing boundaries, peer-review requirements, acceptance rules, execution environment profiles, harness capabilities, RHOAI model substitutions, and contracting controls.

Model-profile registries include deployment_tier, benchmark_gate, and promotion_status fields so practical defaults and enterprise evaluation targets are visible in dispatch envelopes as well as docs.

Run Readiness

The run readiness plan is the pre-handoff control that proves a broad CWO run has owners, exit conditions, validation evidence, artifact authority, provider provenance, quarantine handling, boundary negative tests, next-version deferrals, and handoff evidence before workers execute.

The schema is schemas/run-readiness-plan.schema.json. The sample input is examples/sample-run-readiness-plan.json. The readable template is templates/run-readiness-plan.md. The operator reference is references/run-readiness.md. 

python3 scripts/validate_run_readiness_plan.py \
  examples/sample-run-readiness-plan.json
python3 scripts/render_run_projection.py \
  examples/sample-run-readiness-plan.json --projection run-sheet
python3 scripts/render_run_projection.py \
  examples/sample-run-readiness-plan.json --projection wrap-up-status
python3 scripts/import_execution_telemetry.py --file usage-sidecar.json
python3 scripts/render_execution_status_report.py --format terminal
python3 scripts/render_execution_status_report.py --format terminal --layout expanded
python3 scripts/render_execution_status_report.py --format terminal --layout summary

The key field is the criterion-to-evidence matrix: every acceptance criterion must point at an artifact, validator, or review gate. The rubric owns the criterion IDs, and the matrix proves each one. Run sheets, wrap-up/status reports, and next-version rails stay typed projections from Beads; contractor and local-worker returns stay evidence until evaluation and architect adjudication. The execution status report is a separate end-of-plan accounting view over explicit audit and evaluator artifacts. Its default terminal layout is a compact dashboard for 80-column, half-height terminals, the expanded layout fans out long utilization cells into readable rows, the summary layout keeps the grouped table, expected but unavailable calls, retries, token counts, and timings are shown as ?, and structurally irrelevant telemetry is shown as n/a.

Allowed projection types are run-sheet, wrap-up-status, and next-version. Allowed next-version reasons are out-of-scope, needs-credential, needs-research, hardening, later-version, and blocked. Patrol or recurring work remains research only until ownership, locking, history, failure_containment, and provider_neutral_execution are accepted.

Experts

Expert profiles calibrate the reasoning lens for documentation, architecture, security, web design, editorial review, Red Hat product areas, and other disciplines. Contractor handoff packets include the matched profile by default so review output is grounded in the intended role.

Operator terminology: The exact job-description labels, such as contract-jd-security-reasoning, and executor IDs, such as claude_architecture_critic or gemini_architecture_critic, are technical reference terms. Narrative pages introduce the plain workflow first.

The editor profile uses contract-jd-editorial-reasoning as the final reference label for public docs, README/install docs, GitHub Pages, and documentation-architecture work. It checks reader flow, redundancy, circular content, draft-like wording, and publishable narrative before publish sanitization.

The architecture profile uses contract-jd-architecture-reasoning. When the user explicitly asks for Claude, Gemini, or both as second opinions on a Codex architect design, routing can create independent contractor-only critique lanes with claude_architecture_critic and gemini_architecture_critic. Claude uses claude --model claude-opus-4-6 --effort high -p or stronger effort for higher-complexity architecture. The returns are evaluated evidence, not replacement architecture authority. Gemini/Agy returns are salvage-only by default: they can inform alternate framing, missing cases, and risk notes, but they do not count as primary synthesis inputs unless the architect explicitly upgrades a specific evaluated finding. The acceptance decision may report advisory recommended_synthesis_use, but synthesis still enforces provider-camp policy and readiness.

agy -p is the local CLI surface for the gemini_architecture_critic executor key.

The master-plan profile uses contract-jd-master-plan-review. When the user explicitly asks for ChatGPT Pro 5.5 Extended Reasoning to review the final execution plan or total work packet, routing can select chatgpt_pro_browser_master_reviewer. The result is share-link evidence for Codex plan revision, not implementation authority and not OpenAI Deep Research. For real Pro reviews, the dispatch JSON must include a confirmed model_attestation; otherwise the return is invalidated instead of used. Explicit Pro master review requests are blocking gates before implementation; failed confirmation, dispatch, ingest, evaluation, or adjudication requires operator repair or an explicit Beads-recorded waiver/downgrade before the work can continue.

The operator-calibrated execution profile uses contract-jd-operator-calibrated-execution. Use it when a work packet needs execution-discipline review: current instruction fit, evidence classification, safety-deferred residual risk, false-closure checks, artifact hygiene, and requested closeout such as validation, commit, push, or handoff. The prompt coach reports this as operator_calibration: required for false-closure, not-run, safety-deferred, exhausted-lane, or conflicting-review closeout language; recommended for autonomous, publish, commit/push, mixed-evidence, or multi-target work; and off for ordinary focused tasks.

Red Hat lenses include OpenShift Platform, OpenShift Application Developer, OpenShift AI, Red Hat OpenStack Services on OpenShift, Advanced Cluster Management, Advanced Cluster Security, and Red Hat Enterprise Linux with Identity Management and Satellite sub-specialties.

Codex Beads Hooks

Codex lifecycle hooks can inject Beads recovery context at session start, prompt submit, and compaction boundaries. If the shell displays that context, treat it as a presentation issue: keep bd codex-hook SessionStart as the full-context path unless the installed Codex binary supports a stable visibilityHint display hint. 

python3 scripts/configure_codex_beads_hooks.py \
  --project-dir . \
  --mode full-context \
  --json

python3 scripts/configure_codex_beads_hooks.py \
  --project-dir . \
  --mode quiet \
  --apply

Quiet mode fails closed when support is not detected. The degraded profile requires --allow-degraded-context because memories-only context is not equivalent to the full Beads hook. The operator reference is references/codex-beads-hooks.md, and the reader-facing page is Codex Beads Hooks.

Durable Memory

Closure-memory comments are the compact recovery record for future agents. Use scripts/close_bead_with_summary.py before closing meaningful Beads and fill the recovery fields: who was involved, what changed, why closed, how validated, when closed, where executed, decisions, evidence, residual risk, and follow-up. Pass --meaningful to fail fast when a non-trivial closure is missing required recovery fields.

Beads context depth controls how much of that durable record an internal agent should read. none performs no Beads lookup. summary reads assigned-Bead JSON without comments. focused reads assigned-Bead comments as internal evidence. heavy adds broader related history when prior work or synthesis matters. audit is reserved for incident, quarantine, or forensics work. Outside contractors do not receive raw Beads comments; they get boundary-checked packets. 

python3 scripts/close_bead_with_summary.py \
  --bead "<id>" \
  --disposition completed \
  --why "accepted change validated" \
  --who "Codex main thread; reviewer lane or operator if applicable" \
  --what "docs/use-cases.html added" \
  --how "python3 scripts/validate_repository.py and python3 scripts/validate_site.py" \
  --when "main at <commit-sha>; CI run <id>" \
  --where "repo path; branch main; Beads local-only or Dolt-backed" \
  --decision "kept exact contract labels in reference pages" \
  --evidence "Pages deploy run <id>" \
  --residual-risk "none known" \
  --follow-up "none" \
  --meaningful \
  --close

If bd dolt remote list reports no remotes, record Beads as local-only in the --where field. Do not claim remote sync, CI success, Pages deployment, or publication until those checks have actually completed.

Validation

Publication work should pass repository validation, site validation, unit tests, install smoke checks, browser checks, and publish sanitization before pushing upstream. For meaningful Beads, add a final closure-memory comment before closing so future agents can recover who was involved, what changed, why it closed, how it was validated, when it closed, where executed, residual risk, and follow-up from the work graph.

  1. Run validators locally.
  2. Check desktop and mobile rendering.
  3. Scan for local paths, private attribution, tokens, and keys.
  4. Verify GitHub CI, Pages deploy, and live HTTP 200 after push.
  5. Use the incident-response playbook for sabotage, malpractice, or quarantine cases.
