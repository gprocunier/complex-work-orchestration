Installation locations and profile verification

Follow the installation sequence for default setup. Keep the source checkout, installed skill and target project in separate folders. The installer chooses its destination from CODEX_SKILLS_DIR, then CODEX_HOME/skills, then ~/.codex/skills.

For an intentionally isolated/custom installation, run this alternative from your source checkout, using your real destination. Do not combine it with the default sequence blindly:

Terminal

./scripts/install.sh --codex-home /path/to/isolated-codex --yes
python3 scripts/manage_instruction_profile.py install --profile operator-e --codex-home /path/to/isolated-codex --launcher-dir /path/to/private-bin
python3 scripts/manage_instruction_profile.py verify --profile operator-e --codex-home /path/to/isolated-codex --launcher-dir /path/to/private-bin

Start the launcher with the same CODEX_HOME; otherwise it will look for the profile in another home. Check installed/source parity with scripts/check_installed_skill.py --check using the same home/destination environment. A successful dry run did not install anything.

Model settings: the source operator-e profile requests gpt-5.6-sol and does not itself pin reasoning effort; other configuration may supply it. A supported client model/effort override can retain the named profile. Observe the actual runtime settings; neither a file setting nor model self-identification attests prior turns. Update an existing installation without losing local work

  1. Identify your old source, installed destination, current profile and local modifications. Record the revision and inspect the diff; do not reset, stash, or overwrite a dirty checkout to manufacture cleanliness.
  2. Obtain the intended new source in a separate checkout, review release notes and the current profile/routing references, and run its checks. Do not treat a working-tree version label as a published release.
  3. Use that source's installer with the same intended destination. It stages content and retains a backup outside the active skill directory. Verify installed/source parity afterward.
  4. Install/verify the matching named profile, inspecting any modified-managed-file refusal instead of forcing it. Start a fresh named session; an older thread is not upgraded by copying files.

Changed defaults: current task-selected native routing is Luna-first after neutral sizing, with recorded Terra escalation. Spark/v2 fallback records remain historical and cannot grant new dispatch. Old packets, qualifications, budgets or terminal sessions must not be silently reused. Concurrency remains host-qualified preview. Explicit self-maintenance is a separate authority path, not an ordinary setup requirement.

Find and fix the step that failed

Command not found
Verify the prerequisite; reopen the terminal after PATH changes. For a missing launcher use the explicit fresh-profile command in Start Here. Do not add privileged commands or permission bypasses as a generic fix.
Authentication or requested model unavailable
Complete vendor sign-in yourself. For the main thread use a supported available model setting while retaining the profile and record the deviation. Delegated worker identity/qualification still has to pass; no silent substitution.
Profile verify reports modified files
Inspect the exact paths and compare with the intended source. Keep custom files/evidence. Do not pass --force without deciding which bytes should win.
Skill check reports drift
Confirm the intended source and destination first. README/install-only drift is still drift, but it is not proof every runtime file changed. Do not install an unrelated dirty checkout wholesale.
Beads backend unavailable
Run bd version and follow that release's local backend setup. An empty ready list is valid; a connection error is not. Local records are not synced without a configured Dolt remote.
Native tool/host gate fails
Keep the failed-check evidence and record which processes and resources were stopped. Check the exact model, available tools, MCP integrations, sandbox, source revision and worker qualification. A configuration check or tool list does not prove that the worker can complete real assignments.
A worker is stopped or a dependent task is blocked
Verify that the worker has stopped, account for the time or usage it consumed, and identify which tasks depend on it. Continue unrelated work only if it is already authorized and its own checks pass. Do not resume a stopped attempt or start tasks whose prerequisites have not been accepted.

Task closure and handoff controls

scripts/close_bead_with_summary.py records closure memory before optionally closing a task. A meaningful closure requires who was involved, what changed, how and when it was validated/closed, where it ran, evidence, residual risk and follow-up. It also records why the task is closing and the decision.

The exact options and validation belong to the closure helper; the readiness reference owns the handoff packet and stopping rules. A summary is not proof the checks ran.

Find exact reviewer and tool identifiers

Use the exact executor IDs and capabilities in the executor registry, with the corresponding access profile. For packet, evaluation and adjudication commands, use the contracting reference. Registry names do not prove current runtime availability.
