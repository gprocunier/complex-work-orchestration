Policies

The skill is a small control plane over Beads task tracking: policy chooses routes, schemas define exchanged artifacts, experts calibrate review lenses, and scripts enforce gates.

Policies are JSON-compatible YAML files used by helper scripts. They describe route classes, executors, providers, experts, sharing boundaries, peer-review requirements, acceptance rules, and contracting controls.

Routingpolicy/routing-policy.yaml
Executorspolicy/executor-registry.yaml
Providerspolicy/provider-registry.yaml
Expertspolicy/expert-registry.yaml

Schemas

Schemas make helper outputs reviewable: prompt coach results, route results, contractor handoff packets, contractor returns, local dispatch envelopes, acceptance decisions, audit events, and attestations.

Experts

Expert profiles calibrate the reasoning lens for documentation, architecture, security, web design, editorial review, Red Hat product areas, and other disciplines. Contractor handoff packets include the matched profile by default so review output is grounded in the intended role.

Operator terminology: The exact job-description labels, such as contract-jd-security-reasoning, and executor IDs, such as gemini_3_1_pro_preview_agy, are technical reference terms. Narrative pages introduce the plain workflow first.

The editor profile uses contract-jd-editorial-reasoning as the final reference label for public docs, README/install docs, GitHub Pages, and documentation-architecture work. It checks reader flow, redundancy, circular content, draft-like wording, and publishable narrative before publish sanitization.

The architecture profile uses contract-jd-architecture-reasoning. When the user explicitly asks for a Gemini/Agy second opinion on a Codex architect design, routing can create a contractor-only critique lane with gemini_3_1_pro_preview_agy. The return is evaluated evidence, not replacement architecture authority.

The master-plan profile uses contract-jd-master-plan-review. When the user explicitly asks for ChatGPT Pro 5.5 Extended Reasoning to review the final execution plan or total work packet, routing can select chatgpt_pro_5_5_extended_reasoning_browser. The result is share-link evidence for Codex plan revision, not implementation authority and not OpenAI Deep Research. For real Pro reviews, the dispatch JSON must include a confirmed model_attestation; otherwise the return is invalidated instead of used.

Red Hat lenses include OpenShift Platform, OpenShift Application Developer, OpenShift AI, Red Hat OpenStack Services on OpenShift, Advanced Cluster Management, Advanced Cluster Security, and Red Hat Enterprise Linux with Identity Management and Satellite sub-specialties.

Scripts

Helper scripts are the implementation surface that Codex can run inside the workspace. The user-facing path is still the guided Codex workflow; this section is for exact command lookup, automation, and CI.

Scripts perform sizing, routing, stale-agent cleanup, scaffolding, packet building, dispatch prompt rendering, return normalization, evaluation, audit verification, and repository validation. Scaffolded and expert-review Beads carry native skills, acceptance, design, and notes fields so the work graph is queryable instead of relying only on description text. 

python3 scripts/coach_prompt.py "<task text>"
python3 scripts/route_work.py "<task text>"
python3 scripts/cleanup_stale_agents.py --json
python3 scripts/chatgpt_browser_review.py --packet master-plan-review-packet.json --confirm-only --json
python3 scripts/chatgpt_browser_review.py --packet master-plan-review-packet.json --json
python3 scripts/ingest_chatgpt_share_return.py "<share link>" --bead "<id>"
python3 scripts/workspace_mutation_guard.py --snapshot --output before.json
python3 scripts/validate_repository.py
python3 scripts/validate_site.py

The Workflows guide shows the in-Codex helper sequence, project-manager flow, and manual claude -p, gemini -p, or agy -p contractor handoff.

Deep Dives

Contractor and local-worker pages are specialized workstream references. Use them after the coach has selected the workstream and the user has approved the relevant external-sharing or local inference boundary.

The local-worker deep dive shows the first-class /plan path, --local-ok opt-in, --local-profile openshift-ai-vllm profile selection, dispatch envelope generation, return evaluation, and architect adjudication. The local-worker return is evidence until architect adjudication accepts follow-up work.

Local-worker evaluation starts with the base evaluate_return.py --file local-return.md command. Add --peer-review-required only when route policy, provider-conflict handling, or evaluator context requires peer review for that return.

Validation

Publication work should pass repository validation, site validation, unit tests, install smoke checks, browser checks, and publish sanitization before pushing upstream.

  1. Run validators locally.
  2. Check desktop and mobile rendering.
  3. Scan for local paths, private attribution, tokens, and keys.
  4. Verify GitHub CI, Pages deploy, and live HTTP 200 after push.
