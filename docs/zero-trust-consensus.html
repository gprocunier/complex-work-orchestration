Zero-Trust Consensus

Multiple models can agree and still be wrong. CWO compares structured claims across independent trust domains, reports agreement and divergence, and keeps final authority with the architect.

Problem Flow Structured Claims Normalization Trust Domains Divergence Guardrails Model Synthesis Return Guardrails Reference Index

The Problem

Cross-model review is valuable because different providers, local deployments, and model families catch different issues. The mistake is treating agreement as proof. Shared training data, copied assumptions, benchmark pressure, provider policy, and prompt wording can make several models converge on the same weak answer.

Zero-trust consensus makes that risk explicit. It records which inputs counted, which were excluded, what claims were comparable, and where independent trust domains disagreed. The output is evidence for architect adjudication, not a release approval.

Simple rule: agreement can reduce uncertainty, but it never becomes validation by itself.

Structured Claims

CWO does not infer security claims from fluent prose. The synthesis input must carry explicit zero_trust_claims with stable claim IDs, categories, keys, values, claim types, and evidence. This keeps the comparison deterministic and reviewable. 

{
  "claim_id": "auth:jwt_algorithms",
  "category": "auth",
  "key": "jwt_algorithms",
  "value": "RS256 only",
  "claim_type": "security_assertion",
  "evidence": "Reviewer cited the configured allow-list."
}

Supported categories live in policy/zero-trust-consensus-policy.yaml. The initial set focuses on security-sensitive areas such as cryptography, authentication, network behavior, dependencies, concurrency, data handling, privilege boundaries, and supply chain concerns.

Claim Normalization

CWO reduces only narrow formatting noise before comparing claim values. Short technical identifiers in cryptography, authentication, and network categories can match across common punctuation or spacing differences, such as AES-256-GCM and aes256gcm.

The normalizer does not rewrite URLs, paths, configuration fragments, version-like values such as TLS-1.2, or ordinary prose. That keeps the comparison useful without turning a formatting helper into semantic approval.

Trust Domains

A trust domain is the independence unit CWO counts. It is not a quality score. CWO resolves it from trust_domain, then provider_family, then provider_camp. Unknown domains and non-primary returns are excluded from the independent-domain count.

Counts Accepted primary synthesis inputs with known trust domains.
Excluded Boundary-tainted, rejected, quarantined, process-held, salvage-only, partial-only, open-risk, unknown, and missing returns.
Minimum Two independent trust domains by default.

Divergence

CWO compares claims with the same claim_id, or the same category:key fallback. If two independent domains make comparable claims with different normalized values, the report records the competing values, the lanes that made them, supporting evidence, and the required resolution owner.

The allowed states are intentionally narrow: informational, blocked, and divergent. There is no validated, trusted, or confirmed state.

Guardrails

  • Required zero-trust consensus blocks synthesis if too few independent domains are available.
  • Material divergence blocks implementation conversion until architect adjudication.
  • Weakness-pattern matches are informational unless another gate escalates them.
  • Excluded inputs remain visible so operators can see what did not count.
  • Agreement remains evidence, not authority; in short, agreement remains evidence.
