How-to

Prompt Coach

The coach compiles a user request into the right orchestration shape: in-thread work, lightweight Beads, full harness, outside contracts, local-worker review, or publish-release gates.

Run It Output Levels Interactive Questions Local Workers Defaults

Run It

In normal use, ask Codex to run the coach from /plan before scaffolding. The shell command is the helper Codex runs behind the scenes or the equivalent for an operator working outside the Codex session. 

/plan Use $complex-work-orchestration prompt coach:
Publish-ready docs with validation and editorial review.

Codex may run this helper behind the scenes. Use direct script execution only for automation, CI, troubleshooting, or an operator shell outside Codex. 

python3 scripts/coach_prompt.py --json \
  "Publish-ready docs with validation and editorial review."

The result includes a recommended orchestration level, route summary, missing questions, enabled levers, disabled levers, and a launch prompt that can be pasted back into Codex.

Output Levels

Output levels are the coach's work-sizing result. They tell Codex whether to stay in the current thread, create a small durable Beads task, open a full work graph, or add a publish, contractor, or local-worker gate.

Graph size is separate from output level. A full graph remains the default for broad orchestration, while tight-chain review requests should use --scaffold-size tight to keep required gates and limit optional expert fan-out.

Default to the smallest level that captures the work story, evidence, validation, and handoff. Escalate when risk, publication, parallel review, or external/local model evidence changes the acceptance path.

In-thread

Current-thread execution with one durable Beads task.

Lightweight Beads

Durable state without a full role graph.

Full Harness

Architect, PM, internal review worker, validation, and handoff workstreams.

External Contract

Contractor-only workstream after explicit outside-sharing opt-in and share-boundary selection.

Local Worker

Bounded local-worker review workstream after explicit local opt-in, evaluator review, and architect adjudication.

Publish Release

Full validation and publish-sanitization before push, tag, or release.

Interactive Questions

In Plan mode, Codex can turn the coach's interactive_questions into selectable prompts. In Default mode, Codex should ask only a blocking concise question or apply the conservative default.

For a complete main-thread helper flow, see the Workflows guide.

Useful choices: harness size, subagent parallelism, outside-sharing boundary, model synthesis, local-worker opt-in, and validation bar. These change execution behavior and should be captured before dispatch.
Architect critique: A prompt such as “Use Claude Opus 4.6 and Gemini 3.1 Pro Preview as independent second opinions on the Codex architect design” should surface the outside-sharing boundary. With explicit opt-in, the coach can route one redacted architecture packet per selected critic. The outside-sharing question appears automatically when explicit external-model or contractor cues exist; otherwise the user can request external review directly. agy -p is the local CLI surface for the gemini_3_1_pro_preview_agy executor key.
Master review: A prompt such as “Use ChatGPT Pro 5.5 Extended Reasoning to review the final execution plan” should surface the outside-sharing boundary and a redacted-packet default. The coach keeps this separate from Deep Research, which remains an explicit research opt-in.
Model synthesis: Explicit fusion, ensemble, model-camp, "more eyes", or synthesis language sets model_synthesis.recommended_mode=requested and active=true. High-risk architecture, provider conflict, or novel design work sets recommended_mode=recommended until the user opts in; accepted opt-in uses recommended_mode=accepted. Advanced helper usage can pass --model-synthesis to coach_prompt.py, route_work.py, or scaffold_workgraph.py to record that accepted state consistently. The lane keeps independent model evidence separate, then records consensus, disagreements, unsupported claims, risk deltas, evaluator dispositions, provider conflict flags, partial or missing lane summaries, and recommended plan revisions for architect adjudication. This is CWO-native synthesis, not direct OpenRouter Fusion dispatch. Gemini/Agy critique is salvage-only by default: it may inform risk notes and follow-up questions, but it does not count toward minimum_usable_inputs unless the architect explicitly upgrades a specific evaluated finding. Evaluated returns expose evidence_quality_score and advisory recommended_synthesis_use so generic advice is visible; synthesis remains authoritative for primary, salvage-only, open-risk, rejected, quarantined, and readiness classification.
Scaffold size: scaffold_sizing records whether the graph should be full or tight. Tight-chain is for focused review work where the primary expert lane and required gates are enough. 
python3 scripts/scaffold_workgraph.py \
  --title "<goal>" \
  --description "<scope>" \
  --scaffold-size tight
Beads context depth: beads_context_depth sizes how much durable Beads history internal Codex agents read. none performs no Beads lookup, summary reads the assigned Bead without comments, focused includes assigned-Bead comments, heavy adds broader related history, and audit is for incidents, sabotage, forensics, or quarantine review. The compatibility alias beads_briefing_depth matches the same value. The coach records provenance for computed, requested, and effective depth. 
python3 scripts/build_beads_brief.py \
  --bead "$BEAD_ID" \
  --depth focused \
  --for subagent
Comment-bearing briefs are internal only. Outside contractors use build_contractor_packet.py.
Subagents: broad docs, Pages, policy, routing, test, validation, and publish-sanitization work should surface a workerbee_parallelism choice. The coach always asks whether to parallelize with subagents. Narrow work can default to no subagents; broad review work can use review-only or heavy review subagents with Codex 5.3 Spark when available, or the smallest available capable review model. Implementation subagents still require explicitly disjoint scopes.
Publication work: README, install docs, and GitHub Pages changes need a final editorial review before publish sanitization. That review should translate control-plane terms into reader-facing language unless the page is an explicit reference.

Local Workers

Local-worker language such as vLLM, OpenShift AI, or local worker makes the coach ask for local opt-in unless --local-ok is already present. The recommended default is no local dispatch.

The reason to use a local worker is not prestige; it is fit. A bounded local reviewer can check command examples, logs, narrow docs, and repetitive evidence without spending frontier model attention on work such as sanity-checking curl output. OpenShift AI is the exemplar model-serving platform for this workflow, but any approved OpenAI-compatible local endpoint can fill the role when policy permits it. 

/plan Use $complex-work-orchestration prompt coach:
OpenShift AI vLLM local review of README command examples.

Codex may run the helper equivalent after explicit opt-in: 

python3 scripts/coach_prompt.py \
  --local-ok \
  --prefer-local \
  --local-profile openshift-ai-vllm \
  --requested-role documentation \
  "OpenShift AI vLLM local review of README command examples."

A local-worker result still needs a local-worker-only / no-codex-exec Bead, dispatch envelope, evaluation, and architect adjudication before any follow-up implementation.

Defaults

Conservative defaults keep work inside Codex, require Beads tracking, disable outside sharing until explicit opt-in, disable local worker dispatch until explicit opt-in, and ask for explicit publish, release, or high-risk signals before forcing publish-grade validation. 

python3 scripts/route_work.py \
  "Security review the auth token and shell command handling."
Durability fallback: If Beads is unavailable, the coach and scaffold can record the task or graph in a temporary Markdown plan file. Durability is reduced, and contractor-only filtering or automatic ready-work features are unavailable.
