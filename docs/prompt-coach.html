Start the planning process

Turn your request into a workable plan

Prompt Coach is the starting point for planning your own project: define success, size the whole job and choose useful help. The practice example already provides a small workflow; you do not need a separate coaching step to try it.

Prompt Coach shapes the brief; the lead turns it into a plan. For consequential choices, approved models can give independent second opinions. The lead checks and synthesizes those findings, revises the plan and saves the tasks. Coaching itself does not call reviewers or authorize implementation.

From your request to a reviewed plan

  1. Define and size. State the result, permitted changes and completion checks. Estimate preparation, implementation, reviews, integration, validation and handoff—not just model calls. Planning-only work estimates those later stages without starting them.
  2. Draft the plan. The lead identifies options, assumptions, dependencies and tests. A small task may stay in one thread with one Beads record. Larger work can use a work graph—a saved set of tasks and dependencies.
  3. Get second opinions when useful. Give each approved reviewer the same starting design and a focused question. Save its findings before showing it the other reviews.
  4. Synthesize and revise. Check evidence, resolve important disagreements and record which findings change the plan. Save unresolved questions and required tests with the work.
  5. Execute only when permitted. A reviewed plan supplies the next tasks; it does not grant new model calls, file changes or publication rights.

See the retry-planning example: two second opinions change an unconditional retry proposal into a plan with explicit server requirements and failure tests. Continue with the project workflow once the plan is accepted.

Copy a multi-model planning request

In a fresh CWO session, ask for the prompt coach before creating the work graph. Use /plan when you want to compare options before execution. Adapt this request to your project and the reviewers you actually want.

/plan Use $complex-work-orchestration prompt coach:
Plan retry handling for our job-submission client. One user request must not create duplicate jobs.
Planning only: do not modify files or deploy.
Compare no automatic retries with retries backed by server-side duplicate protection.
Size preparation, two second opinions, synthesis and validation—not just the model calls.
Also estimate implementation and handoff, but do not start them. Agree the review allowance before either reviewer is called.
Have the coordinating Codex model draft the initial plan.
I authorize a Claude Opus reviewer to receive only a redacted design brief.
I also opt in to a configured local vLLM reviewer receiving that same brief.
Use only available, approved routes; report a missing route rather than substitute a model.
Ask each reviewer independently where the plan can create duplicate jobs and what check would expose it.
Use model synthesis: keep the findings separate, evaluate their evidence, investigate disagreements and revise the plan.
Save the assumptions, required tests, unresolved questions and implementation tasks.
Stop after the reviewed plan. Do not implement, publish or make extra reviewer calls.

Codex may run this helper behind the scenes. Use direct script execution only for automation, CI, troubleshooting, or an operator shell outside Codex. This shorter example shows the helper interface; it does not request the two reviews in the full planning prompt above. 

python3 scripts/coach_prompt.py --json \
  "Plan retry handling for a job-submission client without duplicate jobs."

This is an example request, not evidence of a dispatch. Replace the reviewers and sharing approval with choices you actually intend. If a required route is unavailable, keep that review blocked; do not treat the prompt as proof that the model can be called.

Read the recommended coordination level, proposed reviewer or worker route, missing decisions and warnings. The output also includes a launch prompt you can give Codex after resolving those decisions.

Explicit coach requests also carry requires_user_selection_before_plan and selection_before_plan_reason. When that gate is true, present the coach options before creating a decision-complete plan.

Choose how much coordination the task needs

The coach may recommend one tracked task in the current thread, a set of linked tasks, or a larger graph with implementation, review and validation. Outside review, local models and publication add their own permission and validation requirements.

Graph size is a separate choice: --scaffold-size tight keeps the required stages while omitting optional specialist branches. A full graph is appropriate when broad work has independent responsibilities to coordinate.

Use the smallest arrangement that can deliver the result, check it and save a useful handoff. Add review or other stages when the task’s risk or acceptance requirements justify them.

In-thread

Work in this conversation and save one Beads task.

Lightweight Beads

Save linked tasks without separate assignments for every project role.

Coordinated project (full-harness)

Separate assignments for planning, implementation, review, validation and handoff.

External Contract

An outside-model assignment after you approve the recipient and material to share.

Local Worker

A focused local-model review after explicit opt-in, evidence checks and the lead’s decision.

Publish Release

Run required checks and remove private or temporary content before an explicitly approved push, tag or release.

Set the choices that change the plan

In Plan mode, Codex can turn the coach's interactive_questions into selectable prompts. In Default mode, Codex should ask only a blocking concise question or apply the conservative default unless the user explicitly asked for coach options.

For a complete main-thread helper flow, see the Workflows guide.

Decisions to settle: task size, whether to use subagents, which material may leave the project, whether to compare independent reviews, whether local inference is allowed and which checks define completion.
Selection gate: If requires_user_selection_before_plan=true, wait for the user choice before producing the implementation plan unless the user already asked Codex to proceed.
Architect critique: A prompt such as “Use Claude Opus 4.6 and Gemini 3.1 Pro Preview as independent second opinions on the Codex architect design” should surface the outside-sharing boundary. With explicit opt-in, the coach can route one redacted architecture packet per selected critic. The outside-sharing question appears automatically when explicit external-model or contractor cues exist; otherwise the user can request external review directly. agy -p is the local CLI surface for the gemini_architecture_critic executor key.
Multiple reviews: preserve each reviewer’s findings, check their evidence and summarize agreements, disagreements and missing support. The lead decides which findings change the plan; see model synthesis.
Check why work is being closed: did the deliverable meet its requirements, or did time, permissions or a failed attempt stop the work? The coach’s operator_calibration setting adds this review when the request indicates false-completion risk or conflicting evidence. It is not required for every small task.
Operator Reference: Model Synthesis Fields

Explicit fusion, ensemble, model-camp, "more eyes", or synthesis language sets model_synthesis.recommended_mode=requested and active=true. High-risk architecture, provider conflict, or novel design work sets recommended_mode=recommended until the user opts in; accepted opt-in uses recommended_mode=accepted. Advanced helper usage can pass --model-synthesis to coach_prompt.py, route_work.py, or scaffold_workgraph.py to record that accepted state consistently. The lane records evaluator dispositions, provider conflict flags, partial or missing lane summaries, and recommended plan revisions for architect adjudication. This is CWO-native synthesis, not direct OpenRouter Fusion dispatch.

Gemini/Agy critique is salvage-only by default: it may inform risk notes and follow-up questions, but it does not count toward minimum_usable_inputs unless the architect explicitly upgrades a specific evaluated finding. Evaluated returns expose evidence_quality_score and advisory recommended_synthesis_use so generic advice is visible; synthesis remains authoritative for primary, salvage-only, open-risk, process-held, rejected, quarantined, and readiness classification.

Focused review: include the assigned reviewer and required checks. Add other reviewers when they address a separate need. The exact compact-graph option is --scaffold-size tight.
Operator Reference: Scaffold Size

scaffold_sizing records whether the graph should be full or tight. Tight-chain is for focused review work where the primary expert lane and required gates are enough. 

python3 scripts/scaffold_workgraph.py \
  --title "<goal>" \
  --description "<scope>" \
  --scaffold-size tight
Beads context depth: Context depth controls how much durable Beads history internal agents read before they work. Use the autosized default unless the task clearly needs less history or a heavier audit pass.
Operator Reference: Beads Context Depth beads_context_depth sizes how much durable Beads history internal Codex agents read. none performs no Beads lookup, summary reads the assigned Bead without comments, focused includes assigned-Bead comments, heavy adds broader related history, and audit is for incidents, sabotage, forensics, or quarantine review. The coach records provenance for computed, requested, and effective depth. The Context option is always present in interactive_questions, with the autosized depth as the recommended default. 
python3 scripts/build_beads_brief.py \
  --bead "$BEAD_ID" \
  --depth focused \
  --for subagent
Comment-bearing briefs are internal only. Outside contractors use build_contractor_packet.py.
Operator Reference: Data Sensitivity Routing infers data_sensitivity with an advisory text heuristic and records data_sensitivity_source, data_sensitivity_heuristic, and data_sensitivity_provenance. Keyword matching can miss paraphrases or context, so operators should declare known boundaries explicitly. 
python3 scripts/coach_prompt.py --data-sensitivity restricted "<task text>"
python3 scripts/route_work.py --data-sensitivity redacted "<task text>"
Subagents: Broad docs, Pages, policy, routing, test, validation, and publish-sanitization work should surface a subagent-parallelism choice. Narrow work can stay in the main thread; broad review can use bounded review-only workers.
Operator Reference: Subagent Parallelism

The coach always asks whether to parallelize with subagents and records the answer in workerbee_parallelism. In the connected native path, broad review work uses the exact task-selected Luna-first route only after exact model/host qualification. Historical Spark compatibility records do not grant fresh dispatch. Do not silently substitute another model. A separately selected local or contractor route follows its own profile and approval boundary. Implementation subagents still require explicitly disjoint scopes.

Publication work: README, install docs, and GitHub Pages changes need a final editorial review before publish sanitization. That review should translate control-plane terms into reader-facing language unless the page is an explicit reference.

Decide whether a local model is useful

Local-worker language such as vLLM, OpenShift AI, or local worker makes the coach ask for local opt-in unless --local-ok is already present. The recommended default is no local dispatch.

Choose a local model for a specific task it can perform and a data boundary it is allowed to use. Examples include checking a command, small diff or short log excerpt. A deterministic check may be enough without any model call. OpenShift AI is the documented serving example; other approved OpenAI-compatible local endpoints can use the generic profile.

/plan Use $complex-work-orchestration prompt coach:
OpenShift AI vLLM local review of README command examples.

Codex may run the helper equivalent after explicit opt-in: 

python3 scripts/coach_prompt.py \
  --local-ok \
  --prefer-local \
  --local-profile openshift-ai-vllm \
  --requested-role documentation \
  "OpenShift AI vLLM local review of README command examples."

A local answer still needs a separate, focused assignment and a saved request. Check its evidence and record the lead’s decision before changing the project.

What happens when you do not opt into extra routes

By default, keep the work inside Codex with a Beads record. Do not dispatch outside reviewers or local models without explicit opt-in. Publication and high-risk work require their own checks; a recommendation from the coach is not permission to perform those actions.

python3 scripts/route_work.py \
  "Security review the auth token and shell command handling."
Durability fallback: If Beads is unavailable, the coach and scaffold can record the task or graph in a temporary Markdown plan file. Durability is reduced, and contractor-only filtering or automatic ready-work features are unavailable.
