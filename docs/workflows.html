Workflows

A fresh Candidate E session is the normal CWO entry point. It runs the coach, turns answers into a Beads-backed plan, and supervises one bounded native Spark worker when delegation is worthwhile. Optional contractor, local-worker, and concurrent lanes remain separate.

Start Candidate E

After the one-time profile setup in Get Started, start a fresh session in the repository that owns the work: 

cwo-codex -C "$PWD"

Candidate E is CWO's default instruction profile for the Codex session that owns scope, integration, acceptance, and handoff. The profile is selected at process startup, so resuming an older Codex thread does not activate the named profile or provide its selection evidence. Explicitly reading and following the prompt remains a distinguishable fallback when a fresh process is unavailable. See Get Started for install, rollback, and explicit-profile details.

Invoke From Codex

The normal interface is a Codex request, not a manual tour of helper scripts. Ask for the skill and prompt coach in /plan; Codex can run the local tools, summarize the route, and ask only the choices that change execution. If another approved shell is already driving the work, run the helper directly and select the matching execution profile.

If you need examples before choosing a route, start with the simple prompt-coach path or the complex multi-expert review pattern.

Coach And Decide

The coach decides whether the work should stay in-thread, use a lightweight Beads task, scaffold a full harness, or add publish gates. If the route involves outside sharing or local inference, Codex asks for that explicit boundary before any contractor handoff packet exists. A packet is a policy-checked bundle of share boundary, job labels, task context, and approved snippets prepared for outside or local review.

This page owns the full lifecycle. The Prompt Coach guide owns the narrower request-sizing details and launch-prompt composition.

Beads Task Graph

Beads is mandatory durable memory. A Beads task graph is the work ledger of tasks, dependencies, evidence, and handoff state. For narrow work, use one task. For broader work, Codex creates an epic with workstreams for architect framing, implementation, review, validation, handoff, and publish-sanitization. Public docs and GitHub Pages work adds a publication review so documentation, web design, and final editorial review converge before validation is accepted.

Durability fallback: If Beads is unavailable, record the same task or graph structure in a temporary Markdown plan file and note that durability is reduced. Do not claim shared ready-work semantics or durable external handoff unless Beads or an equivalent tracker is actually in use.

For the reader-facing rationale and exact context-depth controls, see Beads Memory.

Run Readiness

Before worker handoff on broad, reviewed, synthesized, public, or release-sensitive work, Codex should prove the run is ready to execute. The readiness plan keeps Beads as the durable source of truth and records the execution checks workers need before they start.

The gate names each workstream owner, exit condition, validation evidence, authority rule, boundary negative test, next-version item, and handoff evidence requirement. It also records which outside or local findings were accepted, rejected, or quarantined by architect adjudication.

Run sheets, wrap-up/status reports, and next-version rails are generated views from the durable work state. They help humans review and hand off the run, but they do not become a separate source of truth.

Closure pressure starts at acceptance or independent validation. The PM reuses the current work unit rather than creating routine repair Beads, and records a retain, correct, quarantine, defer, or close disposition.

  2. The readiness plan names owners, exits, and evidence.
  3. The architect adjudicates accepted and rejected findings.
  4. Workers receive handoff evidence instead of transcript guesses.

Delegate Through Native Supervision

Candidate E can keep narrow work in its own session. When a narrow implementation or validation task merits delegation, the normal connected path uses one fresh native Spark worker. The local supervisor—the trusted controller outside the worker—verifies the session, binds the exact assignment and limits, arms observation before submission, and watches the task until it closes. Every delegated native worker is supervised; there is no unsupervised mode or opt-out.

  1. Record acceptance criteria, scope, dependencies, and validation in Beads.
  2. Use trusted no-tools attestation; a model self-report is not identity proof.
  3. Persist and arm supervision before sending the task.
  4. Submit, bind the receipt, and begin one-second checks in one uninterrupted control turn.
  5. Interrupt and contain on model, tool, budget, workspace, telemetry, or control failure.
  6. Validate the artifact before Candidate E accepts it.

The Native Supervision guide explains the lifecycle, workspace authority, recovery rules, and operator references. Multi-worker concurrency, not supervision, is the experimental feature. Pools of two or three workers are an explicit opt-in Tech Preview; capacity four and above is blocked.

Optional Workstreams

Contractors and local workers are specialized workstreams selected by the coach and route, not separate starting points. Use them only after the user approves the relevant sharing or local-inference boundary.

Execution profile matters. Connected Codex runs may opt in to outside contractors after the share boundary is approved. Restricted profiles must follow their policy gates before any outside sharing. Airgapped profiles assume no Codex CLI dependency and disable outside contracting; they rely on local Beads plus OpenCode or a manual operator shell with approved local model serving.

A packet validation checkpoint verifies the share boundary, opt-in basis, disclosure level, artifact whitelist, expert profile, and packet integrity before a manual dispatch prompt is rendered.

Outside-contractor workstream: If the coach suggests outside contracting and the user approves third-party sharing, Codex can build the contractor lane. The External Contracting guide shows packet building, prompt rendering, mutation guards, claude -p and agy -p calls, and browser master-review setup and ingestion.

The underlying helpers are scripts/build_contractor_packet.py, scripts/dispatch_work.py, scripts/workspace_mutation_guard.py, scripts/launch_chatgpt_cdp_chrome.sh, scripts/chatgpt_browser_review.py, and scripts/ingest_chatgpt_share_return.py; the rendered contractor prompt is typically captured as contractor-dispatch-prompt.md.

Boundary rule: Use --external-ok only after the user approves third-party sharing. Use --allow-disclosure-escalation for repo-readonly or patch-branch handoff packets. Do not use external-contractor wording for airgapped profiles unless the environment policy has explicitly changed.
Redacted CLI dispatch: If an external CLI can inspect the current directory, run a redacted-packet prompt from a neutral directory or treat any unapproved repository inspection as invalid contractor evidence.

Execution Environments

Codex is the default connected execution environment. CWO keeps the durable memory, route policy, review gates, validation, and handoff shape separate from the shell that performs the work.

That separation is what makes the disconnected path credible. OpenCode is the first open-source harness exemplar. OpenShift AI vLLM is the local serving exemplar. Other approved shells or OpenAI-compatible endpoints can use the same envelope, evaluator, and architect-adjudication pattern.

Validate And Handoff

Validation is the final gate, not a cleanup step. Record commands, evidence, screenshots, return evaluation, and residual risk in Beads before the architect accepts the work.

Meaningful closures also need a final closure-memory comment before bd close. Keep the close reason short and place the reusable brief in the comment: who was involved, what changed, why it closed, how it was validated, when it closed, where it ran, decisions, evidence, residual risk, and follow-up. Pass --meaningful to enforce those fields for non-trivial Beads. That record is what a spawned agent or compacted session reads when the transcript is missing or fuzzy.

The final CWO answer also needs an operator handoff packet: next executable Bead, why it is next, exact command/resume, execution prompt, what must not run yet, commit/push status, validation status, and escalation rule. Include it even after implementation, commit, push, PR update, or publication work.

The exact closure helper syntax lives in Reference. Keep this page focused on the lifecycle: validate, record evidence, close with recovery context, then verify the published result. Codex may use scripts/close_bead_with_summary.py behind the scenes when it closes meaningful work.
