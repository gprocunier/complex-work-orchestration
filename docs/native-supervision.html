Delegated work

Native Worker Supervision

Candidate E keeps the decisions. When CWO delegates a narrow implementation or validation task, the local supervisor—the trusted controller outside the worker—verifies a fresh Spark session, binds the assignment, and watches it until it closes. Supervision is mandatory for every delegated native worker; multi-worker concurrency is the optional Tech Preview.

Supervision Is Mandatory For Delegated Workers

Native supervision is the normal connected-Codex control when CWO delegates reading, editing, or validation after the important decisions are closed. Every delegated native worker is supervised. Once CWO delegates to a native worker, there is no unsupervised mode or opt-out. Multi-worker concurrency is the experimental part, not supervision. Most tasks use one fresh gpt-5.3-codex-spark worker with one policy-checked assignment that fixes the workspace, scope, tools, limits, and required validation.

Candidate E owns architecture, scope decisions, integration judgment, and acceptance. The worker may read, edit, or validate only what its assignment permits. Its return is evidence until the Candidate E session checks the result.

Before Dispatch

CWO estimates the work before it builds a dispatchable packet. A packet is the policy-checked assignment given to a worker: it names the exact workspace, scope, permitted actions, limits, and validation. The estimate records expected behavior, affected contracts, command complexity, reads, mutations, validation, and budget. A separate zero-tool precommit check tests whether the proposed assignment fits those limits.

An accepting precommit receipt binds the exact work plan, but it still does not authorize repository work. The release step must also bind the packet, requested model, canary evidence, and adjudication state. A changed work plan needs a fresh worker, prompt, nonce, and receipt.

Evidence is not authority: A packet hash, receipt, preflight result, or worker statement cannot widen the task or authorize dispatch by itself.

The Live Control Turn

The local supervisor persists supervision state and registers the observer before it sends the task. Arming, submission, receipt binding, polling, interruption, and finalization share one control-turn identity.

  1. Persist: write the bound supervision state before any triggering action.
  2. Arm: register the observer and prove trusted telemetry is available.
  3. Send: submit the exact released task to the attested session.
  4. Bind: attach the returned submission identifier to this control turn.
  5. Check: compare trusted events with the packet every second.
  6. Resolve: interrupt on a violation or observe a clean terminal state.
  7. Finalize: record terminal, budget, telemetry, and workspace receipts.
  8. Close: end supervision only after the evidence is durable.

No assistant or model round-trip may occur between task submission and the first check. A long passive wait is not live monitoring. If interrupt, close, wait, or trusted telemetry is unavailable, CWO stops before dispatch rather than substituting another route.

The supervisor compares trusted events with the packet: model, tools, command results, reads, mutations, validation, tokens, runtime, compaction, terminal state, and workspace drift.

The Packet Owns The Workspace Boundary

The packet's declared working directory is authoritative. A worker can inherit a different shell directory, but that inherited value cannot widen where it may read or write.

CWO records a clean baseline, resolves allowed paths, and checks live changes against the packet. Unexpected untracked files, out-of-scope writes, incomplete comparison, aliased worktrees, or symlinked authority boundaries stop the attempt.

Multi-Worker Concurrency Is A Tech Preview

Running multiple supervised workers concurrently is experimental and disabled by default. Supervision remains mandatory for every worker; only the concurrent pool requires a separate opt-in.

One workerStandardNormal mandatory supervision controls.
Two workersOpt-in Tech PreviewFresh same-host capability and safe fixed cohort.
Three workersOpt-in Tech PreviewReleased and hard ceiling.
Four or moreBlockedNot represented by the operative contract.

A concurrent pool requires deterministic admission, an economical and schedulable cohort, immutable child bindings, and either isolated mutable worktrees or a strictly shared read-only topology. Precommit, packet construction, critics, integration, retry, replay, and publication remain single-flight.

Do not imitate a pool by running several single-worker supervisors in parallel. Productive concurrency uses the admission-bound version-2 host path and consumes one-use live authority.

The Tool-Boundary Activation Preview Is Separate

Ordinary supervised workers require exact server-side tool allowlisting. A disabled detect-and-contain preview explores a weaker boundary in which an unlisted built-in could act before detection. It is not the normal supervisor and is not equivalent to prevention.

The preview accepts only three fixed profiles: n1-read-only, n2-read-only, and n1-mutable. Dry-run validation does not consume the approval. A live attempt needs a signed exact-attempt approval, a permanent one-use claim, explicit risk acceptance, and --enable-tech-preview. Its artifacts prove only that specific certification run.
