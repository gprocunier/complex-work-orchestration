Confirm you can delegate this task

Registered single-worker execution requires the original signed workflow, explicit consent for the exact provider request and separate production authentication. The registered contained pool is also enabled for real use. Legacy serial pool and retry execution, live campaigns, live activation, dedicated tool-surface capture and maintenance observation production are retired. Raw native launch and standalone pool plans without the protected host remain held. Registered routes continue to use shared tool-surface checks. Find the archived procedures and current checker.

Confirm the host's observed capability evidence for its executable, configuration and enforced tool profile. Check that the worker's actual model matches the selection for this assignment.

A native worker is another Codex agent assigned a specific task. Every native worker CWO delegates to must be supervised; there is no unsupervised opt-out. A small, explicitly authorized maintenance task can stay in the main thread. Use delegation when it helps the project, not merely to demonstrate another agent.

This page explains the steps; it does not approve a launch. The active policy and trusted host must establish the exact worker model, allowed tools, workspace, ownership, time and usage allowance for this attempt.

See the supervision overview: scope, monitoring, observed work, cleanup and acceptance.

Size the whole assignment before choosing the worker

Size the assignment first. The shipped worker policy points to the Luna role’s current model for focused native work. Sol handles recorded coding escalation. Terra handles explicitly classified interface, visual and computer-use work, including coding tasks whose main deliverable is an interface. Each role has a current and previous model in the routing configuration. You can opt in to the latest visible model in a role's family at startup or use an explicit pin.

For each attempt, verify that the observed model matches the requested model and that the assignment, source revision and allowance match the approved records. A CLI accepting a model name, or a probe showing tools, does not prove the worker can safely complete the task. Do not silently substitute an available model.

The Codex lead, workers and reviewers start at high reasoning effort. Routing can select xhigh for a worker or reviewer and records the reason with the dispatch. It does so after a recorded rejection of a default-effort attempt on the same delivery, for security or containment work, for independent review of a high- or critical-risk change, and for architecture or planning work with wide consequences. route_work.py --json reports the effort and reason for each Codex role. The cwo-codex launcher reads its effort from the Sol role, and configured Sol effort is capped at xhigh: a policy that sets it to max fails validation. The native supervision reference lists the routing signals under “Reasoning effort routing”.

Optional cyber fallback after a refusal

The shipped policy has no cyber_fallback role. If your account has Daybreak Blue access, you can add the role to your installed policy/model-roles.yaml. It names its own exact Sol-family model, which must differ from the Sol role’s model, and runs that model with daybreak=true. CWO never sets daybreak=true on any other model. At startup CWO checks the Codex model catalog and reports the role as unavailable when the model or the Daybreak Blue access program is missing.

Only a structured cyber-policy refusal from a model other than the fallback triggers it, and only for work you have marked in an owner-only private file outside every lead and worker write root. The same task, with the identical packet, then runs once, with the original reasoning effort capped at xhigh and on the standard service tier, on the cyber_fallback model, and the attempt is charged against the original budget again. A second refusal or an account without Daybreak Blue access stops the task. Unmarked work and any other refusal, error or timeout also stop it. Each escalation is recorded in the audit with the refusal that triggered it and its outcome. The lead’s model never changes, and adding the role or a mark does not enable any held route.

If you enabled this role before 1.48.0, update its model as the 1.48.0 changelog entry describes. The native supervision reference has the role entry and the mark file format.

The normal single-worker path

You set the goal, allowed changes, spending and sharing boundaries. Ask the lead agent to prepare the assignment and report whether the exact worker route is available. The lead prepares and checks the execution records; you inspect the result and decide whether it meets your need. This overview is not a substitute for the exact execution contract.

  1. Record the required result, allowed changes and acceptance checks. Estimate preparation, execution, review, integration and validation before choosing a worker.
  2. Check the selected model, host and tool capabilities, and present ownership. Verify enforced filesystem/network boundaries.
  3. Prepare a fresh attempt with four distinct records: a fit check without tool access (precommit, not a Git commit), the scoped assignment (packet), approval for that exact assignment (operative release evidence) and a finite time/usage allowance. Passing the fit check alone does not approve execution.
  4. Save the control state and register monitoring before sending the assignment. Use the host-approved launch procedure (admitted transaction) so the supervisor can observe, interrupt and close the worker. Follow the exact execution contract.
  5. Check the product behavior and which files actually changed. Confirm owned processes and resources are closed, evaluate the return, then record the lead’s acceptance decision.

If the assignment needs an operator-authorized comparison of independent reviews, arrange original capture and evaluation under the separate review controller account. The lead can request that comparison by its approved reference. See review custody and source counting.

A finished connection or a worker’s claim of success is not proof that the task passed. A request to revise the assignment (realignment) is not completion. A stopped attempt cannot be resumed; another attempt needs its own fresh allowance.

Registered contained pools

One trusted controller can run two or three independent approved assignments together. Each app server sees a read-only checkout and reaches only the model provider. The registered writer alone can create the approved output in its worker’s checkout.

Before starting, the controller verifies separate configured worker logins, the exact cohort and shared allowance, and measures its callbacks on the same host. The native integration checks the installed Codex CLI for the protocol capabilities required from version 0.163.0 onward. Keep Beads updates, integration and publication in their normal order.

To set up the logins, run python3 scripts/setup_delegation.py from the installed skill directory with --pool-worker-home given once per worker, using a separate home for each. Approve the ordered group and its shared allowance with the foreground delegation tool from the project checkout, then run cwo delegate-pool --pool-request <request-path> from the same checkout. Productive work starts only after calibration and admission of the whole cohort succeed.

The live containment record covers both cohort widths, a local writer failure, shared accounting and cleanup. It records offered tools as observations. Confidential operation is unsupported.

Pool contracts, admission, interruption and cleanup preserve the details and historical evidence. Read-only work needs enforced read-only access. Do not treat a return as read-only when consistent evidence reports a mutation.

After a failure, determine which work must stop

After a failure, check whether the worker has stopped, who owns its resources, what allowance it consumed and which tasks depend on its result. A CONTAINED state label does not prove cleanup finished. Preserve failed and UNKNOWN observations. Continue unrelated, already-authorized work only if its own checks pass; dependent work waits for its prerequisite to be accepted.

Inspect the transaction and failure-accounting implementation; the recovery helper does not promise automatic replay of a terminal attempt.

Self-maintenance is a separate explicitly adopted objective. Its owner must grant the required in-process permissions and bound each operation. A saved authority record is not itself permission to execute. These maintenance controls are not required for ordinary first use.

Read the diagram as text
  • The attempt on task A has ended and cannot be resumed. Preserve its failure evidence, including failed and UNKNOWN observations.
  • Inspect actual process stop, resource ownership, changed files and consumed allowance. A CONTAINED status is not proof that these checks passed. Unresolved shared safety or capacity problems can still prevent other work.
  • Task B depends on accepted A and must wait. A replacement of A is a distinct attempt: it needs new permission, a fresh allowance and verified acceptance. B may start only after A is accepted and B’s own checks pass.
  • Task C does not depend on A’s result. It may continue only if its own permission, prerequisites, safety and shared capacity pass. A child failure does not by itself end all parent work.

Use older records to understand past runs, not to launch new ones

The source references retain Spark/v2 packets, fallback semantics and qualification records for interpreting earlier runs. For a fresh assignment, use the active routing policy and the model configured for the role.

The dedicated tool-surface capture and maintenance observation producers are archived in v1.48.0. The current scripts/check_maintenance_qualification.py verifies successful, unexpired version 3 observations using the recorded digest, the exact issuing control image and the original session file. Follow the production requirements link in the native source contract for archive locations and the separately governed signed N1 host qualification.
