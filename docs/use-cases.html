Look at the work, not the org chart

Each example starts with a problem, gives you a usable prompt, and shows what an accepted result must contain. Choose the reason for extra structure—not a number of agents.

The configuration checker has a documented live two-session run on one Linux host. The other three are explicitly authored, executable evidence exercises, not customer stories, actual reviewer transcripts, or benchmarks. Their results demonstrate the checks, not universal runtime integration.

1. A change that survives a fresh session

Problem: a validator repair and a CLI depend on the same contract. Restarting must not reopen why booleans are invalid ports.

Initiating prompt; full runnable steps in Start Here

Use $complex-work-orchestration. In a disposable project, fix the validator first and record its accepted behavior. Create a dependent CLI task but leave it unstarted. Save task IDs, exact checks and a readable handoff. Continue in a fresh session using only project files and Beads. No production access or publication.

Operator decision: approve the list-of-errors API and scope. CWO records two tasks, verifies the prerequisite, and uses the saved decision to bound the second phase. Do not delegate this small exercise just to demonstrate a worker.

Validator: accepted; booleans are not ports.
CLI: depends on accepted validator; same error interface.
Evidence: tests, diff, task records, HANDOFF.md.
Authority: disposable local project only.

The excerpt is illustrative; the full tutorial creates actual IDs and artifacts. The live run finished with an agent-produced checker, 11 project tests, and two completed linked tasks. Stronger final contract checks were then run independently. Execution versions and limits.

Recovery: if the next session cannot establish acceptance, recheck files/tests and task records before implementing the CLI; mark missing evidence honestly. Not worth it: a throwaway one-line conversion with no meaningful continuation.

2. Resolve contradictory retry proposals with a counterexample

Problem: proposal A says retry transient failures for all requests; proposal B says retrying a non-idempotent write can duplicate its effect. These are genuinely contradictory authored proposals, not fabricated returns from real reviewers.

Initiating prompt

Use $complex-work-orchestration to review our retry design in a synthetic fixture. Compare “retry all transient failures” against “never replay non-idempotent writes.” Reproduce the counterexample; do not call a real API. Preserve both proposals, evidence and the owner’s decision. Do not implement until the acceptance invariant is settled.

Operator decision: whether the service supplies an actual idempotency guarantee. The fixture assumes it does not. CWO separates that assumption from implementation advice and records the rejected alternative rather than voting on reviewer confidence.

Invariant: a POST must not silently produce two effects.
Proposal A, POST: 2 attempts, 2 effects — rejected.
Proposal B, POST: 1 attempt, 1 effect — ambiguity surfaced.
Bounded GET retry: 2 attempts, 0 write effects — permitted.
Decision: retry reads; do not replay ambiguous writes.

Concrete output: a decision record with its assumption, counterexample, accepted policy and rejected policy. The executable fixture asserts each count. This is not a complete HTTP retry library.

Recovery: if later evidence proves server-side idempotency, reopen that assumption in a new bounded task; do not erase the earlier evidence. Not worth it: a retry-free offline transformation with no disputed effect.

3. Rehearse a configuration rollout without touching production

Problem: a staged configuration passes a shape check but the running service might not become healthy. “The file looks correct” is not acceptance.

Initiating prompt

Use $complex-work-orchestration to prepare a lab-only configuration change. Identify the execution host and exact writable paths before any mutation. Stage the candidate, preserve the prior bytes, define a health check and rollback trigger, then verify restored state after a failed check. No production hosts, privilege escalation, deployment or remote access is authorized.

Operator decision: name the real lab host and approve any actual service action in a separate task. CWO must not infer production authority from an infrastructure-flavored prompt.

Boundary: temporary local files only; no network requests.
Stage: port 8081, prior port 8080 preserved.
Health: intentionally simulated failure.
Recovery: restore prior content, reread active.json.
Acceptance: restored_port=8080; rollback_verified=true.

Concrete output: a run record, staged/previous configuration, explicit failed health observation, and verified restoration. The fixture uses temporary local files and asserts restored content. It does not prove service restart, remote reachability, a real health check, or lab deployment.

Recovery: failed rollback stops the affected operation; retain the backup and evidence, do not continue dependent rollout. Not worth it: inspecting a static file without any intended change.

4. Turn source notes into a defensible decision memo

Problem: a team must choose an error-output format. Source notes mix a requirement, a reproducible fact and an unsupported performance claim. A polished summary can still launder the unsupported claim into “truth.”

Initiating prompt

Use $complex-work-orchestration to turn the supplied synthetic notes into an output-format decision memo. Trace every material claim to a note, run the available representation check, and exclude unsupported performance assertions. Produce decision.md plus claim-sources.json. Keep unresolved client compatibility as a human decision. Do not invent research, contact external sources, or publish.

Operator decision: confirm that downstream clients accept the proposed format. CWO keeps the requirement and evidence with the artifact and bounds further research instead of generating endless prose.

N1: clients need a list of messages — requirement.
N2: JSON round-trips the nested list — checked.
N3: JSON is always faster — unsupported, excluded.
Decision: JSON preserves the required shape (N1, N2).
Remaining: client compatibility, not an invented speed claim.

Concrete output: the memo text and source mapping are returned in fixture JSON. The representation assertion is executed; the notes themselves are synthetic inputs, not findings from external research.

Recovery: contradictory/new sources reopen only the affected decision, preserve earlier provenance, and rerun the corresponding check. Not worth it: paraphrasing one uncontroversial paragraph with no retained deliverable.

A substantial artifact: rebuilding a documentation system

Sanitized local example: this documentation set was maintained as a source-to-artifact project. The starting mismatch was concrete: the active worker policy selected Luna first while reader pages still described Spark as normal. Installation instructions existed, but not a complete useful first task and verified fresh-session continuation. This is a local implementation example, not a deployed-site claim or a productivity benchmark.

Initiating prompt for a documentation project

Use CWO to rebuild the human documentation around adoption. Audit current implementation and classify every document before editing. Give one editor ownership of the integrated copy. Build a complete novice project and a direct experienced-operator route. Map material claims to source evidence, preserve historical qualification, keep old URLs useful, and verify examples plus the rendered site. Do not change runtime policy or publish.

Operator decision: select the source baseline and publication boundary; resolve disputed product promises against implementation, not marketing preference. CWO records dependencies between the truth audit, integrated first slice, independent reader review, expansion and final validation. Reviewer praise does not replace executing the tutorial.

Decision: one canonical first-project sequence; README summarizes and links.
Source: active task-selected policy, installer/profile code and actual tests.
Maturity: exact host qualification is required; historical Spark records stay historical.
Artifact: README + reader pages + runnable examples + maintainer ownership map.
Compatibility: retain 16 page routes and 139 existing IDs.
Observed defect: four links existed in the repo but failed under the Pages subpath.
Correction: explicit source links plus a regression for the published-root boundary.

Acceptance: inspect the rewritten pages and canonical ownership/checks; execute both tutorial sessions, run claim/link/example checks, and inspect desktop/mobile and keyboard behavior. The source-to-claim record, page migration map, review dispositions and raw local evidence are work artifacts, not extra public navigation. Recovery: preserve accepted copy and failed evidence, correct the affected link or command, and rerun the relevant check rather than restarting the whole project. Not worth it: correcting a single typo with no behavioral or navigation effect.

Run and inspect the three evidence exercises

These exercises require only Python 3, Git, and a CWO source checkout. You do not need Codex authentication, Beads, an installed skill, or a model call. Choose a new source-only evaluation folder. If ~/cwo-example-source already exists, use another name or inspect that checkout instead of deleting it.

Terminal

python3 --version
git --version
git clone https://github.com/gprocunier/complex-work-orchestration.git "$HOME/cwo-example-source"
cd "$HOME/cwo-example-source"
python3 examples/worked-evidence/run_examples.py --check

Expected: JSON with the retry effect counts, rollback_verified: true, and a memo excluding N3. All three exercises run in temporary local storage without model calls; generated temporary files are removed after their contents are captured in output. On failure, inspect the failing assertion; do not use production access to make a demo impressive.

For the actual agent exercise, use Start Here. For advanced controls, use Guides and Reference.
