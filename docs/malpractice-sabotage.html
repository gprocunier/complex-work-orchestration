Malpractice And Sabotage Guardrails

CWO treats every model return as untrusted evidence. Good advice can still be wrong, unsupported, boundary-breaking, or harmful until it passes evaluation and architect adjudication.

Zero Trust

A model can produce a useful critique and still include unsafe instructions, invented evidence, accidental disclosure, or advice that violates the approved work boundary. CWO therefore separates useful content from authority. The return is evidence until it is checked.

This applies to outside contractors, local workers, synthesis inputs, and internal review lanes. The controls are not limited to hostile behavior; they also catch sloppy or unverifiable work that would make a future agent less safe.

  1. A model return arrives from an approved lane.
  2. CWO checks whether the return stayed inside its packet and mutation boundary.
  3. Evaluation scores malpractice and sabotage signals.
  4. The return receives a disposition such as accepted, rejected, or quarantined.
  5. The architect decides whether any finding changes the plan.

Signal Types

Malpractice signals focus on negligent or low-quality behavior: unsupported claims, missing validation, command claims without evidence, unsafe shortcuts, or guidance that ignores the stated scope. Sabotage signals focus on adversarial or boundary-breaking behavior: prompt injection, secret seeking, unauthorized repo inspection, destructive recommendations, or attempts to bypass the review process.

No guarantee language: these checks reduce risk and create a review path. They do not promise that every bad return will be caught automatically.

Boundary Example

A reviewer receives a redacted packet that contains only a plan summary. Its return says it inspected repository files and found a failing test. That might be a useful clue, but it also means the return used context outside the approved packet. CWO should mark the finding as a boundary violation, keep it out of primary synthesis, and ask the architect whether to investigate the clue through an approved lane.

Allowed evidence Comments on the plan text included in the packet.
Out-of-scope evidence Claims based on files, commands, secrets, or local state that were not shared.
Safe handling Quarantine the return or downgrade it to a follow-up question until the boundary is resolved.

Quarantine

Quarantine is the safe holding pattern for evidence that cannot be trusted yet. A quarantined return may still contain useful clues, but those clues should not flow into implementation, synthesis, release notes, or public docs until the architect has resolved the boundary and evidence problem.

  • A boundary-tainted return does not become a primary synthesis input.
  • Unsupported claims stay visible as risk, not accepted fact.
  • Unexpected workspace changes require mutation-guard review.
  • Incident response uses the canonical playbook instead of ad hoc cleanup.

The public incident-response reference is linked from Validate And Handoff and from the exact controls in Reference.

Publication Work

Public docs and GitHub Pages have their own failure mode: internal planning text can accidentally become reader-facing product copy. CWO treats that as a publication-quality issue. The final review should remove internal labels, draft notes, private paths, unsupported claims, and authority-confusing wording before the work is pushed.

Continue with Model Synthesis for how evaluated returns are combined, or use Reference to find the exact controls.
