Malpractice And Sabotage Guardrails

CWO treats every model return as untrusted evidence. Frontier, local, and open-weight models can all be useful, but provider policy, deployment rules, training choices, tool access, and operating context can still shape what they return. The terms malpractice and sabotage name evidence-quality and boundary-risk categories; they are not accusations of intent.

Zero Trust

A model can produce a useful critique and still include unsafe instructions, invented evidence, accidental disclosure, or advice that violates the approved work boundary. CWO therefore separates useful content from authority. The return is evidence until it is checked.

Provider identity, model family, self-attestation, and confident prose do not confer authority. This applies to outside contractors, local workers, synthesis inputs, and internal review lanes. The controls are not limited to deliberate misuse; they also catch boundary-violating, insufficiently supported, or unverifiable work that would make a future agent less safe.

When several accepted returns make comparable security-sensitive claims, Zero-Trust Consensus checks whether independent trust domains agree or diverge. That report is still evidence: agreement is not validation, and unresolved divergence stays with architect adjudication.

Why This Matters Now

Zero trust is the practical baseline for model-assisted work. The point is not to rank providers. The operational issue is that every model has boundaries the operator may not fully see. Good governance therefore needs guardrails, observability, provenance, peer review, and a clear decision owner.

One dated public example makes the control problem concrete. A June 2026 system card describes classifier-triggered safeguards for several high-risk topics, including some frontier AI development work. The cited examples include pretraining pipelines, distributed training infrastructure, and accelerator design.

At the time of publication, that documentation described fallback or blocking behavior rather than a hidden technical mechanism. The durable point is not the specific model version or API behavior. The durable point is that provider policy and client surface can change which model answers, whether a request is answered, and what limitations should be disclosed.

The broader lesson applies across providers and local deployments. Any model can be shaped by provider policy, safety tuning, benchmark incentives, training-data gaps, jurisdictional requirements, endpoint configuration, tool availability, or local deployment rules. The operator cannot inspect every choice that shaped the model, so the output should be routed as evidence, not authority.

Evidence-bound example: this page cites one public provider disclosure because it is concrete and inspectable. It is not a provider ranking. The same zero-trust posture applies to OpenAI, Anthropic, Google, Meta, xAI, local open-weight deployments, and any other model source.

Handlers For Model Work

The useful analogy is handler discipline, not blind trust. In intelligence work, an asset may be valuable while still being untrusted. The handler constrains the assignment, records provenance, cross-checks claims, and escalates contradictions. CWO applies that operating model to model output.

A contractor packet limits what the model receives. The evidence rubric says what a valid return must include. The evaluator scores malpractice and sabotage signals. Peer review and synthesis keep provider provenance visible. The architect decides what can influence implementation.

Signal Types

Malpractice signals focus on unsupported or low-quality returns: unsupported claims, missing validation, command claims without evidence, unsafe shortcuts, or guidance that ignores the stated scope. Sabotage signals focus on boundary-risk patterns: prompt injection signals, sensitive-data requests, unauthorized repo inspection, irreversible-change recommendations, or review-process evasion.

Work-rerouting signals cover a subtler sabotage pattern: the return appears helpful while changing the requested job into a weaker one. Complex Work Orchestration scores objective dilution, non-equivalent substitution, critical-path deferral without an approved tracked follow-up task, and completion claims that omit required acceptance evidence.

Provider-policy signals cover a different failure mode: the return reports, omits, obscures, or mishandles policy constraints that can affect output. An opaque intervention signal, missing provider-conflict disposition, or a claim that peer review is not needed when provider conflict is present should be scored as a review risk.

No guarantee language: these checks reduce risk and create a review path. They do not promise that every unsafe or incorrect return will be caught automatically.

Work Rerouting

Work rerouting is often more dangerous than an obvious hostile instruction because it looks cooperative. A return may keep the same tone and vocabulary while quietly moving the operator away from the required outcome.

The layman version is hiring a locksmith to fix a broken lock and receiving a proposal to repaint the hallway instead. The hallway work may be real work, but it does not secure the door. In software terms, a contractor asked to implement and validate an evaluator cannot satisfy the assignment by recommending a future research note, a documentation roadmap, or an unrelated cleanup.

Objective dilution Required implementation or validation becomes discussion, research, planning, or vague docs work.
Non-equivalent substitution The return proposes a different or easier deliverable and treats it as equivalent to the assigned objective.
Critical-path deferral Acceptance work is moved to later without an approved reason and concrete tracked follow-up task.
Acceptance omission The return claims completion while skipping objective mapping or required validation evidence.

This is how Complex Work Orchestration handles public scorecard-style concerns about models that may subvert or redirect work. The control does not depend on proving intent. If the assigned job is rerouted into a non-equivalent outcome, the return is treated as untrusted evidence and must go through peer review and architect adjudication before it can influence implementation. The signal is a quality gate, not an accusation of misconduct.

Provider-Policy Limitations

A return from a provider-connected model should disclose material provider-policy limitations and name the Provider conflict disposition. Disclosure is not a defect; it is the evidence needed to route the return safely.

Honest disclosure should normally trigger review and provenance tracking, not automatic rejection. The high-risk condition is a return that omits or misrepresents provider limitations, dismisses required peer review, or asks the architect to treat the return as implementation authority.

Conflict domain detected Record provider provenance and require provider-conflict disposition.
Opaque intervention language Score a provider-policy signal and require review before use.
Disposition missing Treat as incomplete evidence and keep peer review active.
Review dismissed Reject the return as authority and escalate to architect adjudication.

Evidence Example

A reviewer receives a redacted packet that contains only a plan summary. Its return includes a claim based on repository files that were not shared. The claim may be a useful lead, but it is not valid evidence for implementation.

Allowed evidence Comments on the plan text included in the packet.
Out-of-scope evidence Claims based on files, commands, secrets, or local state that were not shared.
Safe handling Quarantine the return or downgrade it to a follow-up question until the boundary is resolved.
Disposition Boundary-tainted; not a primary synthesis input until architect adjudication resolves it.

Quarantine

Quarantine is the safe holding pattern for evidence that cannot be trusted yet. A quarantined return may still contain useful clues, but those clues should not flow into implementation, synthesis, release notes, or public docs until the architect has resolved the boundary and evidence problem. Pending peer review or provider-conflict review is a process hold: the evaluator records implementation_blocked, hold_reasons, and hold_classification without converting the substantive verdict to quarantine.

  • A boundary-tainted return does not become a primary synthesis input.
  • Unsupported claims stay visible as risk, not accepted fact.
  • Provider-policy limitations require provider provenance and disposition.
  • Unexpected workspace changes require mutation-guard review.
  • Incident response uses the canonical playbook instead of ad hoc cleanup.

The public incident-response reference is linked from Validate And Handoff and from the exact controls in Reference.

Publication Work

Public docs and GitHub Pages have their own failure mode: internal planning text can accidentally become reader-facing product copy. CWO treats that as a publication-quality issue. The final review should remove internal labels, draft notes, private paths, unsupported claims, loaded provider rhetoric, and authority-confusing wording before the work is pushed.

  • No private paths, command guesses, or internal planning labels.
  • No model-asserted claim without artifact evidence or source provenance.
  • No authority inflation: a model return is evidence, not proof.
  • No provider-policy claim without a source, limitation note, or disposition.
