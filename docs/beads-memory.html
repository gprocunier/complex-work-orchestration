Continue a project from saved work

Save decisions outside the conversation, recover them after compaction or a restart, and check the current project before continuing.

Check what is complete and verified

A new session needs the current files, accepted decisions and next ready tasks. Beads stores tasks and dependencies; comments and linked artifacts explain what was checked and accepted. Save those details so another person or agent can verify the same starting point.

Start with the checkout, HANDOFF.md, task IDs and linked evidence. Finish this check with one of three answers: the next task is ready, a named prerequisite is missing, or the requested work is complete.

Read saved records after compaction or a restart

Compaction summarizes a long conversation so it fits the model’s working context. Earlier details may no longer be available there. Starting a fresh session creates a similar continuity problem: the next agent needs the project state, not an assumed memory of the last conversation.

Durable memory means records kept outside that conversation. Beads is the task database CWO uses: task status and dependencies identify the work, while notes, comments and linked evidence preserve decisions. Project files hold the actual code, tests, reports and handoff. Neither store replaces the other.

  1. Record as work proceeds. Keep requirements, accepted decisions, checks and remaining work with their task. Link the files and reports that support the decision; do not wait for compaction to write them down.
  2. Read the relevant project record. After compaction or a restart, recover the current task, its prerequisites, accepted evidence, unresolved questions, remaining budget and attempt limits. A stopped attempt remains stopped.
  3. Compare the record with the current project. Inspect the current checkout and source revision, compare them with the saved record, and rerun the checks the next task depends on. Continue only work whose prerequisites and permissions still hold. If records are missing or disagree, investigate and name the block rather than inventing continuity.

This workflow reduces reliance on the conversation, but it cannot reconstruct decisions that were never recorded. The diagram illustrates the intended recovery process; it is not a new observed compaction trial.

What belongs in the project record?

Beads: the task and decision record
Requirements and acceptance criteria; owners, status and dependencies; what was accepted and why; unresolved risks; the next permitted action; and links to supporting files and checks.
Project files: the work and its evidence
Code and tests, the source revision, validation reports and an explicit handoff. Record the commands and results needed to check the accepted behavior again—not just “tests passed.”
What not to treat as current authority
An old conversation summary, a ready task, a closed-task label or an outdated report. Each can help locate evidence; none alone proves that the current checkout is ready or permits a new action.

The closure helper reference lists the fields for saving a meaningful task decision. Save a compact, verifiable record—not every message from the chat.

How context gets back into the session

When configured and supported by the installed Codex and Beads versions, Beads hooks—commands run at session or conversation events—can supply or refresh project context. CWO’s configuration helper emits startup, prompt and pre/post-compaction hook commands. That configuration is not proof that every host executes every event correctly.

Hooks do not manufacture missing decisions or replace the explicit read-and-verify step above. Use the commands below to inspect the actual task record. Internal assignments can receive a selected task brief; outside reviewers must use a brief checked against the approved sharing boundary.

Inspect the actual work record

The documentation-audit CLI case saved separate tasks for its requirements, implementation and independent review. Its database is local and is not included in the source checkout. Read the saved case handoff for the portable record; use task IDs from your own project for live Beads commands.

If a command extends past the edge of its code block, scroll within the block to read it. Copy the complete command, not only the visible part.

Terminal

cd /path/to/your/project
pwd
git status --short
cat HANDOFF.md
bd list --all
bd ready --json
bd show TASK_ID --json

Replace the directory and task ID with the actual project values. Expected: the source, handoff and task agree on accepted behavior, current changes and remaining work. An empty ready list can mean prerequisites are incomplete or the authorized scope is already complete. Do not infer permission from a task being ready.

If the records disagree: stop dependent work, inspect the named source and checks, and record the uncertainty. Do not reconstruct a confident story from the old conversation.

Verify before changing anything

Use the project’s own README and saved commands. For the CLI case, from the CWO source checkout containing this change:

Terminal

python3 -m unittest discover -s tests -p test_documentation_cli.py -v
python3 scripts/check_documentation.py --json

Expected: eleven focused tests pass; the new report has version: 1, ok: true and an empty errors list. Rerun these checks rather than relying on an old report. Then confirm the next task’s prerequisites.

Keep the decision with its evidence

Before closing an important task, record what changed, what behavior was accepted, which checks ran, who accepted it and what remains. In the CLI case, review found a real-process encoding failure that an in-memory test missed. The fix used default JSON escaping and a forced-ASCII subprocess test; it did not weaken the Unicode requirement.

The task-closure reference lists the exact helper fields for saving that decision.

Give the next assignment enough context

Give the next assignment its requirements, direct dependencies, relevant files and decisive checks—not the entire project history. Include the source revision and anything that remains uncertain.

Internal agents can receive relevant task history. Outside reviewers receive only a brief checked against the approved sharing boundary, not the full work record.

Back up task records separately

Local-only storage is not remote backup. With a Dolt-backed project, configure and verify a remote separately if you need shared recovery. Inspect current Beads setup before assuming records are synced.
